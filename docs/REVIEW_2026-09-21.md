## Corrected feature inventory

The earlier main-only assessment missed substantial existing work. PR #1 already contains verified-email PIN setup/reset, six-digit PIN login, scrypt hashing, lockout logic, shared-pin photo upload/compression, hazard photos, email notifications, scene ownership/subscriptions/statuses, a smaller splat and mobile-rendering improvements. These are code observations, not proof that every production workflow works.

The most significant gap is connection between features, not lack of a 3D engine. `admin3d.js` still implements personal pins with `sn_uid` and `sn_user_pins` in localStorage. In contrast, the scene editor has server-owned scenes. Those are separate authoring paths and cannot be described as one completed account-owned pin workflow.

## Findings against the three product faces

### Public guide

1. Permanent labels were passive CSS2D elements without a building information card. Existing label properties can safely carry approved description, main landline and real photo metadata; no new GIS layer is necessary.
2. The public viewer parses points/contacts JSON without checking HTTP status or array shape. A JSON error object from a 500 can reach array consumers. The public site map should remain usable, but an outage must not be silently represented as an empty operational dataset.
3. `selectPoint()` replaces the query with `?id=...`, while closing clears it. This loses scene/short-code context. The legacy boot path can also embed scene data into a `d` parameter. Share links must survive selection and refresh without widening scope.
4. The existing frontend requests a complete contacts dataset. `getContacts(baseOnly)` allows contacts not referenced by any scene, not just contacts explicitly approved for public use. Each site's committed static directory contains 98 entries. No entries are reproduced in this report. Public building landlines must be separated from the authenticated staff dropdown; repairing the database alone is not a privacy review.
5. The main splat is 10,928,960 bytes; PR #1's lite asset is 8,743,168 bytes, a 20% transfer reduction, not a fivefold improvement. Retain existing optimization work before experimenting with a new renderer.

### Staff-generated guides

1. Personal pins belong to a browser, not the signed-in employee. Clearing storage or changing device loses access. Login does not make localStorage account-owned.
2. Personal pins cannot hold photos because the photo table references server-side points. The current UI asks users to promote a pin to shared/public to attach a photo. Saving a private draft, adding a photo, and publishing a scoped guide must be separate operations.
3. Photo upload exists, but `_renderPointPhotos()` requests a listing endpoint still gated at viewer membership. Anonymous share recipients cannot discover the image IDs even though the bytes endpoint was made public. An anonymous local request to that real route returns 401. Do NOT fix this by exposing every site's photo listing.
4. Public image access currently relies on knowing a photo UUID. Future unlisted guides need a capability bound to exactly the permitted scene/pin/media; incident evidence must remain authenticated. Publicity and revocation rules must apply to both metadata and bytes.
5. Scene list and deletion use ownership/subscriptions, but scene update/object CRUD and point/photo mutations still often use site-role gates. A filtered list is not object-level authorization. Apply the creator rule, or explicit collaboration permission, to every relevant server operation.
6. Legacy short links use a filesystem JSON store and client-supplied snapshots. This is not a durable, editable, revocable account-owned guide. Some links embed contacts in base64; base64 is not privacy protection. Migrate new shares to canonical database-backed capabilities and define how existing links remain supported.
7. Selected staff contact and per-pin custom phone should not require editing the shared staff directory. Store a pin-local override and expose only the approved public fields.

### Fault/hazard reporting

The newer branch has more than a placeholder: private hazard scenes/photos, notification history, status and email functions exist. The remaining task is a coherent report flow, not a second 3D application. Keep draft/saved/queued/sent/failed states distinct, make retries idempotent, show the reporter a reference, and retain an audit trail. Existing event/webhook modules are reusable, but their existence does not prove reliable end-to-end delivery.

Assura integration is not verified. Public vendor information identifies a configurable workflow platform but does not establish HCMA's enabled API, payload schema or authentication. Start with the existing email adapter and a report-export contract; add an Assura adapter only against the actual authorized tenant interface. Do not promise automatic Assura submission or silently fall back from failed API delivery to duplicate email reports.

## Implementation completed in this checkpoint

- New `location-details.js`: safe optional building metadata, tap-to-call, real-image slot, lazy image decoding, broken-image fallback and no eager building-photo requests.
- Permanent public labels accept touch/click and Enter/Space, retain their existing appearance, open the existing detail panel and stop orbit/fly-to while reading. Rich cards are expanded on mobile; camera controls do not overlap the reading surface. No actual phone, photo or opening-hours data was invented.
- New `guide-url.js`: preserve scene and short-code context, hash and other query values. Do not reuse a legacy embedded payload for a different base pin.
- Viewer boot retains scene context on refresh, avoids baking scene contacts into legacy data URLs and avoids double selection when a short-code URL also contains a pin ID.
- In-flight pin-photo responses are invalidated when opening a building, widget, report or closing the panel, preventing stale images appearing in the wrong card.
- New `public-data.js`: HTTP status and array validation, safe empty fallback for public rendering, and a visible unavailability notice. This does not repair the server's 500s or silently mask staff saves.
- Node unit test command, CI unit/syntax workflow, local-only synthetic browser tests, and read-only deployment/schema preflight scripts.

No changes to production, staff ownership schema, authentication settings, storage policy, mail recipients, map assets, camera presets or real site content were applied. The renderer remains Three.js with the existing splat implementation.

## Validation

21 Node unit tests pass. Chromium acceptance passed at 390x844, 768x1024, 1024x768 and 1440x900, with eight workflow checks per viewport and no page JavaScript errors: no eager photos; detail/photo/call/text safety; keyboard and optional-field reset; broken image; scene-link refresh without embedded data; stale-photo isolation; short-code refresh/close; and public continuity during a simulated HTTP 500. The final extra unit test for legacy pin payload ownership was added after that browser matrix; it does not change scene/s short-code behavior.

Browser tests use synthetic metadata, mock API responses, loopback hosting and data-saver mode. Write requests are intercepted, not delivered. They do not certify real login, uploads, mail delivery, live database permissions or phone GPU performance. A full-splat headless screenshot attempt timed out; that is not evidence of a real-device rendering failure. Test on physical iPhone Safari and mid-range Android before claiming mobile performance readiness.

AGY Gemini 3.8 Flash generated the helper modules, integration patch and tests. Exact-source application and subsequent validation caught an incorrect URL-encoding expectation, raw control-character validation and stale-photo handling; these were corrected. Luna provided an independent gap audit and bounded patch review. Its runtime-compatibility concern was removed from this patch by retaining the existing engine declaration; the dependency/runtime mismatch remains a release checklist issue. Its repeated-label-listener concern was checked against code: `renderBuildings()` currently runs once at boot and creates new labels; no repeated binding to an existing element is introduced. Scene reload/disposal remains a future design consideration.

## Release gate

Do not merge/deploy the accumulated PR #1 solely because this bounded viewer patch passes. First repair and verify live data access, audit private/public contact and media boundaries, qualify PIN setup/login/reset with synthetic accounts, verify all required migrations/storage/mail configuration, and confirm the active deployment target. Retain rollback artifacts. The actual public building photos and main numbers require site approval.
